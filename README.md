# Software-design-doc
The client is The Gaming Room, a company that currently offers its party game “Draw It or Lose It” only as an Android application. They engaged Creative Technology Solutions to design a web-based version that works across desktop browsers, tablets, and mobile devices. The core requirements are support for concurrent multiplayer games, one or more uniquely named teams per game, uniquely named players per team, guaranteed uniqueness of game and team names, a single authoritative game-management service in memory, and a domain model that remains independent of any specific user interface or deployment technology.

What did you do particularly well in developing this documentation?
I clearly separated the domain model (Entity, Game, Team, Player, GameService) from any UI or infrastructure concerns and consistently applied the Singleton and Iterator patterns to meet the uniqueness and single-instance requirements. The Evaluation table thoroughly compared platforms against the client’s multi-platform and cost goals, and the Recommendations section translated those findings into a concrete, production-oriented architecture.

What about the process of working through a design document did you find helpful when developing the code?
Writing the design document first forced me to define the class relationships, factory methods, and uniqueness rules before writing implementation code. This reduced rework because the inheritance hierarchy, encapsulation boundaries, and Singleton constraints were already settled, making the subsequent coding phase more straightforward and less error-prone.

If you could choose one part of your work on these documents to revise, what would you pick? How would you improve it?
I would expand the System Architecture View section. Currently it is left largely empty. Adding a clear logical topology diagram that shows the browser/mobile clients, reverse proxy, GameService containers, PostgreSQL, and Redis, together with the communication paths (REST and WebSocket), would give readers a more complete picture of how the domain model fits into a distributed deployment.

How did you interpret the user’s needs and implement them into your software design? Why is it so important to consider the user’s needs when designing?
I translated the client’s need for multi-platform reach, concurrent multiplayer support, and name uniqueness into a pure-Java domain model that uses a Singleton GameService and Iterator-based uniqueness checks. Keeping the model free of platform-specific APIs ensures the same core logic can later be exposed through any front-end. Considering user needs is essential because software that does not solve the actual problem or respect constraints such as cost, scalability, and cross-platform access will fail to deliver value regardless of technical elegance.

How did you approach designing software? What techniques or strategies would you use in the future to analyze and design a similar software application?
I began with the stated functional and technical requirements, extracted common attributes into an Entity base class, applied the Singleton pattern for the central service, and used factory methods plus the Iterator pattern to enforce uniqueness. In future projects I would continue to start with a clear domain model, apply established design patterns where they directly address requirements, keep presentation and infrastructure concerns separate, and evaluate platform options against cost, scalability, and operational constraints before committing to an architecture.
